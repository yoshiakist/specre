# Getting Started with specre

A step-by-step guide to adopting specre in your project and beginning Spec-Driven Development (SDD) with AI agents.

By the end of this guide, you will have:

- The specre CLI installed and ready to use
- specre initialized and configured in your project
- `glossary.toml` optimized with your project's domain vocabulary
- Your AI editor connected to specre via MCP, enabling agents to use specre as their primary method for code exploration
- A base prompt (CLAUDE.md, etc.) with behavioral guidelines for your coding agent
- The `/specre-whats-next` command ready to recommend your next action

## Prerequisites

- A Git-managed project
- An AI coding editor (Claude Code, Cursor, Windsurf, etc.)

---

## Step 1: Install specre

### Pre-built Binary (Recommended)

```bash
# Linux / macOS
curl --proto '=https' --tlsv1.2 -LsSf https://github.com/yoshiakist/specre/releases/latest/download/specre-installer.sh | sh

# Windows (PowerShell)
powershell -ExecutionPolicy ByPass -c "irm https://github.com/yoshiakist/specre/releases/latest/download/specre-installer.ps1 | iex"
```

### Via Cargo (Rust Users)

```bash
cargo install specre
```

Requires Rust 1.85 or later.

### Verify Installation

```bash
specre --version
```

If a version number is displayed, the installation was successful. If you see `command not found`, check your PATH in the next step.

---

## Step 2: Check Your PATH

If `specre --version` works correctly, skip this step.

### Linux / macOS

If you used the pre-built binary installer, PATH is configured automatically.

If you installed via Cargo, `~/.cargo/bin` must be in your PATH:

```bash
echo $PATH | tr ':' '\n' | grep cargo
```

If nothing is displayed, add it to your shell configuration file:

```bash
# Add to ~/.bashrc, ~/.zshrc, or ~/.profile
export PATH="$HOME/.cargo/bin:$PATH"
```

After making changes, restart your shell or run `source ~/.bashrc` (or the relevant file).

### Windows

If you used the pre-built binary installer, PATH is configured automatically.

If you installed via Cargo, `%USERPROFILE%\.cargo\bin` must be in your PATH:

1. Open "Edit the system environment variables"
2. Go to "Environment Variables" → User variables "Path" → "Edit"
3. If `%USERPROFILE%\.cargo\bin` is not listed, click "New" to add it
4. Restart your terminal

## Step 3: Initialize Your Project

Run `specre init` in your project's root directory:

```bash
specre init
```

This creates the following files and directories:

| File | Description |
|------|-------------|
| `specre.toml` | specre configuration file |
| `glossary.toml` | Project vocabulary for search hint quality |
| `docs/specres/` | Directory for storing specre cards |

At this point the configuration uses default values. You will customize it manually in the next step.

---

## Step 4: Configure specre.toml

Open the `specre.toml` generated by `specre init` and edit it manually to match your project.

```toml
# Where specre cards are stored
specre_dir = "docs/specres"

# Directories to scan for @specre markers
# ⚠ Start with a single domain (see below for why)
source_dirs = ["src/auth", "tests/auth"]

# Target file extensions (omit to auto-detect common extensions)
ext = ["rb", "js", "ts"]

# Language for specre card templates (default: "en")
# Currently supports "en" and "ja"
language = "en"

# Health-check thresholds
[health_check]
coverage = 0.30        # Coverage threshold (0.0–1.0)
orphans = 10           # Allowed number of specre cards not linked to source
index_age_hours = 48   # Hours before the index is considered stale
```

### Configuration Details

#### `source_dirs` — Defining the Scope

The set of directories specre manages. Coverage calculations and marker scanning are performed against files within these directories.

**Always start with a single domain.** There are two important reasons:

1. **Sense of progress**: If the scope is too broad, coverage stays perpetually low, making it hard to feel any progress — and adoption stalls.
2. **Agent trust**: When coverage is low, `health-check` returns `unhealthy`, and coding agents **stop trusting the specre ecosystem**. As a result, even within the target domain, agents will not use `specre search` or `specre trace` for efficient specification lookups — they fall back to conventional grep and file tree traversal instead. Writing specre cards is pointless if your agent never consults them.

Build up coverage in one domain first, then expand the scope gradually.

```toml
# Good: focused on a single domain
source_dirs = ["src/auth", "tests/auth"]

# Avoid: the entire project from the start
source_dirs = ["src", "tests"]
```

#### `ext` — Target File Extensions

When omitted, specre auto-detects common programming language extensions. Specifying them explicitly avoids scanning irrelevant files (images, config files, etc.).

```toml
# Rust project
ext = ["rs"]

# Web application
ext = ["ts", "tsx", "js", "jsx"]

# Ruby on Rails
ext = ["rb", "erb"]
```

#### `language` — Language Setting

Sets the language of section headings in specre card templates.

- `"en"` (default): `## Related Files`, `## Functional Overview`, `## Scenarios`
- `"ja"`: `## 関連ファイル`, `## 機能概要`, `## シナリオ`

The `/specre-whats-next` diagnostic output also follows this setting.

#### `[health_check]` — Health Thresholds

Thresholds used by `specre health-check` to determine ecosystem health.

| Field | Description | Recommended Initial Value |
|-------|-------------|---------------------------|
| `coverage` | Minimum specre coverage. `0.3` = 30% | `0.30` |
| `orphans` | Allowed number of orphaned specre cards (unlinked cards or missing IDs) | `10` |
| `index_age_hours` | Hours before `index.json` is considered stale | `48` |

Start with low thresholds and ratchet them up as specre cards accumulate. The ideal targets are `coverage = 0.8` or higher and `orphans = 0`.

## Step 5: Set Up AI Workflow Commands and Skills

specre provides workflow commands and skills for integration with AI coding agents. Copying these into your project enables slash commands such as `/specre-whats-next` and `/specre-generate`.

### Source

These are stored in the `.claude/` directory of the [specre repository](https://github.com/yoshiakist/specre).

### Files to Copy

**Commands (slash commands)** — prompts that instruct the AI to execute specific workflows:

| File | Purpose |
|------|---------|
| `specre-whats-next.md` | Diagnose ecosystem health and recommend the next action |
| `specre-generate.md` | Bulk-generate specre cards for uncovered files in a domain |
| `specre-sdd-new.md` | Implement a new feature using the SDD workflow |
| `specre-sdd-fix.md` | Fix an existing feature using the SDD workflow |
| `specre-sdd-quality-improvement.md` | Improve code quality using the SDD workflow |
| `specre-refine-glossary.md` | Refine glossary.toml to improve search hint quality |
| `scripts/source-dir-scope.sh` | Helper script used internally by `specre-whats-next` |

**Skills** — guidelines that the AI references automatically based on context:

| Directory | Purpose |
|-----------|---------|
| `specre-investigate-intent/` | Investigate code's specification intent via specre cards |
| `specre-author/` | Guidelines for creating and editing specre cards |

### For Claude Code

```bash
# Clone the specre repository (temporarily)
git clone --depth 1 https://github.com/yoshiakist/specre.git /tmp/specre

# Copy commands
mkdir -p .claude/commands/scripts
cp /tmp/specre/.claude/commands/specre-*.md .claude/commands/
cp /tmp/specre/.claude/commands/scripts/source-dir-scope.sh .claude/commands/scripts/

# Copy skills
mkdir -p .claude/skills
cp -r /tmp/specre/.claude/skills/specre-* .claude/skills/

# Clean up
rm -rf /tmp/specre
```

### For Other Editors

The placement of commands and skills varies by editor:

| Editor | Commands | Skills |
|--------|----------|--------|
| Claude Code | `.claude/commands/` | `.claude/skills/` |
| Cursor | `.cursor/rules/` etc. | Editor-dependent |
| Windsurf | `.windsurf/rules/` etc. | Editor-dependent |
| Gemini | `.gemini/` etc. | Editor-dependent |

> **Note**: Commands and skills are optimized for Claude Code. When using other editors, adapt the file placement and format to match each editor's custom rules/commands specification.

## Step 6: Configure the MCP Server

Configuring the specre MCP server gives AI agents direct access to specre's search, trace, and coverage features. This is more than just "adding functionality." When the MCP server is active and the ecosystem is healthy, coding agents will choose **specre search and specre trace as their first option** for file search and project exploration — instead of conventional grep or file tree traversal. The result: agents can reach the target specification, source, and test files in 1–2 tool calls, saving context window tokens and improving task accuracy.

The MCP server is started via `specre mcp` and communicates over stdio transport.

### Claude Code

Add the following to `.claude/settings.json` (create the file if it doesn't exist):

```json
{
  "mcpServers": {
    "specre": {
      "command": "specre",
      "args": ["mcp"]
    }
  }
}
```

### Cursor

Add the following to `.cursor/mcp.json`:

```json
{
  "mcpServers": {
    "specre": {
      "command": "specre",
      "args": ["mcp"]
    }
  }
}
```

### VS Code (GitHub Copilot)

Add the following to `.vscode/mcp.json`:

```json
{
  "servers": {
    "specre": {
      "type": "stdio",
      "command": "specre",
      "args": ["mcp"]
    }
  }
}
```

### Windsurf

Add the following to `~/.codeium/windsurf/mcp_config.json`:

```json
{
  "mcpServers": {
    "specre": {
      "command": "specre",
      "args": ["mcp"]
    }
  }
}
```

### Verification

After restarting your editor (or reloading MCP servers), ask the AI agent:

```
Run specre health-check
```

If the agent invokes the specre health-check tool directly (without going through Bash or terminal) and returns results, the MCP server is working correctly.

> **Troubleshooting**: If the MCP server fails to start, check:
>
> - Does `specre --version` work in your terminal? (PATH issue)
> - Does `specre.toml` exist in the project root? (`specre init` not run)
> - Is the JSON syntax in the editor config file correct?

Note: MCP is strongly recommended, but even if it doesn't work, the system is designed to fall back to issuing specre commands via Bash.

## Step 7: Add Behavioral Guidelines to Your Base Prompt

Configuring the MCP server alone is not enough — your coding agent still won't know *when* or *how* to use specre. You need to add **behavioral guidelines based on health-check results** to your project's base prompt (CLAUDE.md, GEMINI.md, CLINE.md, AGENT.md, etc.).

With these guidelines in place, the agent will automatically run health-check at the start of each session. If the ecosystem is healthy, it will proactively use specre search and specre trace for code exploration.

Copy the following template into your project's base prompt file:

```markdown
## specre: Spec-Driven Code Exploration

When specre MCP tools are available, **always run `health-check` before any other specre operation.**
This single call determines the code exploration strategy for the entire session.

### healthy = true

The specre ecosystem — specification cards, traceability links, index, and coverage — is in a
trustworthy state. Leverage it aggressively:

- **Use `specre search`** to locate relevant specre cards.
  The most effective pattern is an AND query combining a **noun** (subject) and an **operation** (action):
  - `specre search "auth login"` — find authentication-related specre cards
  - `specre search "order validate"` — find order validation specre cards
  - Add `--or` only when the AND query is too narrow
- **Use `specre trace`** to navigate between specre cards, source files, and test files:
  - `specre trace <ULID>` — from specre card to all linked source/test files
  - `specre trace <file-path>` — from source file to governing specre card(s)
- **Trust specre cards** as the authoritative description of each behavior.
  Read the card's Scenarios and Related Files before modifying code.

### healthy = false

The specre ecosystem has gaps. Do not rely on specre tools. Fall back to:

- `grep` / `glob` for code exploration
- Reading source files and tests directly
- Treating specre cards as reference material, not the single source of truth
```

### Base Prompt Files by Editor

| Editor | File |
|--------|------|
| Claude Code | `CLAUDE.md` |
| Cursor | `.cursorrules` or `.cursor/rules/` |
| Windsurf | `.windsurfrules` |
| Cline | `.clinerules` |
| Gemini | `GEMINI.md` |
| Editor-agnostic | `AGENT.md` |

> **Why this matters**: A healthy specre ecosystem means every behavior has a specification, every source file is traced, and the index is current. Communicating this state to the agent enables it to find the right files in 1–2 tool calls instead of broad codebase searches. Without these guidelines, the agent may know the MCP tools exist but won't know when to use them.

## Step 8: Optimize glossary.toml

The `glossary.toml` generated by `specre init` contains generic sample vocabulary for specre itself. It does not include your project's domain-specific vocabulary (e.g., "authentication", "order", "payment").

`glossary.toml` directly controls the quality of `specre search` hints. When an agent uses specre search and gets zero results or too many results, glossary terms are used to suggest query refinements. **If your project's domain vocabulary is not in the glossary, the agent cannot reach the target specification card via the shortest path.**

Ask the AI agent to run:

```
/specre-refine-glossary
```

This command automatically:

1. Analyzes domain vocabulary from your project's README and source code
2. Tests current hint quality across diverse search patterns
3. Removes unnecessary generic terms and adds project-specific vocabulary
4. Reports before/after hint quality comparison

> **Run this step before you start creating specre cards.** Glossary optimization affects search efficiency across the entire specre ecosystem — postponing it until after cards accumulate creates rework.

---

## Step 9: Run `/specre-whats-next`

All setup is complete. Ask the AI agent for its first diagnosis:

```
/specre-whats-next
```

This command automatically:

1. Reads `specre.toml` to check your project configuration
2. Runs `specre health-check` to diagnose ecosystem health
3. Recommends **one specific next action** based on the current state

On the first run, coverage will be low because no specre cards exist yet. This is normal. Follow the recommended action to begin growing the specre ecosystem incrementally.

### Run It Repeatedly

`/specre-whats-next` is designed to be run repeatedly. Complete one action, then run it again to get the next step.

```
/specre-whats-next → take action → /specre-whats-next → take action → ...
```

This iterative process expands specre coverage one step at a time, steadily maturing the ecosystem.

## Next Steps

### Choose an Adoption Strategy

How you start creating specre cards depends on your project's test quality and coverage. The [Adoption Strategy Guide](adoption-strategy.md) covers three strategies in detail:

| Strategy | When to Use |
|----------|-------------|
| **Test-Derived Extraction** | Tests are behavior-oriented with high coverage |
| **Code-Behavior Analysis** | Tests are implementation-oriented or coverage is low |
| **Top-Down Domain Decomposition** | Greenfield, major rewrite, or sparse tests |

### Frequently Used Commands

| Command | Purpose |
|---------|---------|
| `/specre-whats-next` | Diagnose and recommend the next action |
| `/specre-generate <domain>` | Bulk-generate specre cards for a domain |
| `/specre-sdd-new` | Implement a new feature using the SDD workflow |
| `/specre-sdd-fix` | Fix an existing feature using the SDD workflow |
| `specre coverage` | Check coverage |
| `specre health-check` | Check ecosystem health |
| `specre status` | List specre card statuses |

### Principles to Keep in Mind

- **One domain at a time** — Don't try to cover everything at once. Finish one domain thoroughly before moving to the next.
- **Trust `/specre-whats-next`** — When unsure what to do next, ask this command.
- **Don't rush to `stable`** — `draft` is an honest state. Only promote to `stable` after confirming that implementation and tests match the specification.
- **Don't aim for perfection** — 100% coverage of the entire codebase is not the goal. The goal is to cover every behavior under active development.
